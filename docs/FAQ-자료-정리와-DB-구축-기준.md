# FAQ 자료 정리와 DB 구축 기준

> 역할: 양품화 매뉴얼 사이트 본문을 제목·내용 중심 FAQ로 재구성하고 검토하는 규칙. DB 물리 구조는 `DB-스키마-설계-초안.md`, 항목 작업 원본은 `FAQ-DB-통합-원본.md`를 따른다.

> 현재 상태(2026-11-12): 초기 FAQ 38건 승인·적재 후 V4 참고 FAQ로 확장. V1~V17 SQL 파일이 저장소에 있으며, 최신 버전의 개발 DB 적용 여부는 각 DB의 `flyway_schema_history`에서 확인 필요. 검색은 백엔드 API로 연결됐고 한국어 검색 품질 검증은 진행 중.

## 1. 목적과 적용 범위

- `yangwiki` 프로젝트의 디벗 양품화 매뉴얼 내용을 근거로 상담용 FAQ를 만들고 FAQ 검색 사이트에 적용한다.
- 원문 본문은 FAQ의 근거 자료이며, 원문 전체를 FAQ 레코드로 복사하지 않는다.
- 이 문서는 FAQ 추출·검토·승인·DB 설계·사이트 적용 작업의 기준으로 사용한다.
- 작업은 Phase별로 진행하고 현재 Phase의 완료 기준을 충족한 뒤 다음 Phase로 이동한다.

## 2. FAQ 자료 범위와 작성 기준

- FAQ 작성의 기준 자료는 `C:\Users\guswo\Desktop\개인 프로젝트\yangwiki`의 양품화 매뉴얼 사이트 본문이다.
- FAQ 후보는 `pages/`의 양품화 매뉴얼 사이트 본문을 기준으로 작성한다.
- 사이트가 인용한 별도 PDF·PPTX 파일은 확인 대상에 포함하지 않는다.
- 원본 경로와 출처 필드는 FAQ 원본·DB에 두지 않는다.
- FAQ에 필요한 내용은 매뉴얼 사이트 본문에 있는 안내 범위에서 작성한다.
- 사이트 본문에 없는 정책·일정·금액·연락처·절차를 추측해 추가하지 않는다.
- 연도별 금액·수리 방법·취급 기업 등 차이는 적용 연도와 대상을 본문에 명시하거나 항목을 나눠 정리한다. 연도별 차이나 변경 가능성만으로 `검토 필요` 처리하지 않는다.
- 조건을 명시해도 의미를 확정할 수 없거나 사이트 본문 안에 직접 충돌하는 기준은 FAQ 후보에 추정 내용으로 두지 않는다. 사용자에게 직접 확인한 뒤 합의된 내용을 반영한다.

- 학교명·학생명·계정·비밀번호 등 개인정보나 비밀정보를 FAQ에 옮기지 않는다.

## 3. FAQ 후보 작성 규칙

- 한 항목은 상담원이 검색해 독립적으로 안내할 수 있는 주제 하나를 다룬다. 자료가 질문 형태가 아닐 수 있으므로 모든 제목을 질문으로 강제하지 않는다.
- 운영 콘텐츠 본문은 `title`과 `content`로 구성한다. 제목을 질문형으로, 내용을 답변형 문장으로 만들 필요는 없다.
- 제목은 검색할 업무 주제를 간결하게 표시한다. 내용은 `~다`, `~입니다` 종결보다 명사형·항목형을 우선하고, `대상:`, `절차:`, `조건:`처럼 정보 성격을 구분한다.
- 같은 기준을 말하는 여러 사례는 공통 내용으로 압축한다. 기기·OS·사업·시기에 따라 적용 결과가 달라지면 조건을 보존해 나누거나 명시한다.
- 원문 한 페이지에서 여러 항목을 만들 수 있고, 한 항목의 내용에 여러 원문 구절이 필요할 수 있다.
- 제목은 항목의 주제를 명확히 나타내고, 내용은 근거의 조건·절차·예외를 보존해 이해하기 쉽게 정리한다. 필요한 경우 제목을 실제 문의 문장으로 쓸 수 있다.
- 중복 항목은 내용의 적용 범위가 같은지 확인한 뒤 통합한다. 조건이나 대상이 다르면 별도 항목으로 유지하거나 구분을 명시한다.
- 원문 재구성만으로 의미를 바꾸지 않는다. 모호한 내용을 보완해야 하는 경우 임의로 결론 내리지 않고 사용자 검토 대상으로 남긴다.
- 후보에는 `초안`, `검토 필요`, `승인`, `제외`, `통합` 등 검토 상태를 기록한다. 승인되지 않은 후보는 운영 DB 데이터로 확정하지 않는다.
- `status`와 검토 메모는 작업 문서에서만 사용하며 FAQ 운영 필드에는 포함하지 않는다.

## 4. FAQ 운영 데이터 필드

기존 기획에서 정의한 FAQ 콘텐츠 필드는 다음 6개다.

| 필드 | 기준 |
|---|---|
| `id` | MySQL이 자동 증가 숫자로 생성한다. 새 FAQ 등록 때 직접 지정하지 않으며 시연 데이터 ID를 운영 ID로 가져오지 않는다. |
| `category` | 대분류. 현재 기준은 `2027년 양품화 사업`, `유지보수`, `2027년 디벗 재배치·여분기기 수거 사업`이다. |
| `topic` | 대분류 안의 세부 업무 주제. 아래의 확정 목록에서 선택하고 분류 기준을 일관되게 유지한다. |
| `title` | 상담원이 검색하고 목록에서 확인할 항목의 제목이다. 질문형으로 한정하지 않는다. |
| `content` | 승인된 근거를 바탕으로 한 안내 내용이다. 설명·절차·조건·예외를 포함할 수 있다. |
| `keywords` | 제목에 나타나지 않는 별칭·현장 용어·검색 표현을 보완한다. 실제 검색 사례에 도움이 되는 표현만 기록한다. |

- 검색은 ID·제목·내용·키워드를 대상으로 한다. 제목 일치에 더 높은 우선순위를 두는 것은 현재 기획의 검색 동작을 계승하는 기준이다.
- 키워드는 본문 검색을 대체하지 않고 동의어·띄어쓰기 차이 등 표현 보완에 사용한다.
- 검색 키워드는 별도 `faq_keywords` 테이블에 저장하기로 했다. API에서는 `keywords` 배열로 제공한다.
- 사용 횟수는 FAQ 콘텐츠 필드에 넣지 않는다. 답변 열기 집계는 별도 구조로 관리한다.

### 확정 Topic 목록

| 대분류 | Topic |
|---|---|
| 2027년 양품화 사업 | 사업 일반, 수거 일정, 수거 대상, 지급 품목, 학교 사전준비(OS별), 기타 문의, 관리전환·재배부, 디벗관리시스템, 스마트단말관리시스템 |
| 유지보수 | 시스템·관리, 일반·운영, A/S 및 구매, Chrome, Android, IOS, Windows, Whale |
| 2027년 디벗 재배치·여분기기 수거 사업 | 사업 일반 |

- 양품화 Topic은 업무 흐름에 따라 배정하고, 학교의 사전 조치와 OS별 준비는 `학교 사전준비(OS별)`로 묶는다.
- 유지보수의 OS Topic은 해당 OS·기기 플랫폼에 특화된 안내에 사용한다. `Chrome`은 Chromebook·ChromeOS 관련 안내를 뜻한다.
- Topic 정리는 콘텐츠를 삭제하거나 FAQ ID를 바꾸지 않고 Flyway 신규 마이그레이션으로 수행한다.

## 5. DB와 사이트 적용 원칙

- FAQ 콘텐츠와 회원·인증 데이터, FAQ 이용 집계는 서로 다른 책임의 데이터로 설계한다.
- 현재 데이터 기준은 `id`, `category`, `topic`, `title`, `content`, `keywords`의 6개 필드와 별도 `faq_usage_stats` 집계다.
- 로컬 DB는 MySQL, 서버는 Java·Spring Boot, 빌드는 Gradle Groovy, 로컬 MySQL 실행은 Docker Desktop으로 정했다.
- 카테고리별 FAQ 테이블은 나누지 않고 `faqs` 한 테이블에서 관리한다. 대분류는 별도 `faq_categories` 테이블의 `id`, `name`으로 관리하며, FAQ가 카테고리 ID를 참조한다.
- 현재 검색은 Spring 백엔드의 MySQL 조회 방식으로 구현했다. ID·제목·내용·키워드를 대상으로 하며 띄어쓰기·별칭 등 대표 검색 사례의 품질은 추가 검증한다.
- 실제 인증과 권한 판정은 서버에서 수행한다. 브라우저의 `sessionStorage` 시연 상태는 운영 인증으로 사용하지 않는다.
- 운영 데이터가 검토·승인되고 DB/API 조회가 확인되기 전에는 시연용 `data/faq.json`과 임시 로그인 데이터를 제거하지 않는다.
- 검색 홈·FAQ 목록은 API 요청으로 연결했고 URL 검색 상태·필터·서버 페이징·직접 FAQ 접근을 구현했다. 레거시 `frontend/data/faq.json`은 파일로 남아 있지만 현재 화면 데이터 원본은 아니다.

## 6. Phase 및 완료 기준

### Phase 1. 원본 자료 범위 확정과 FAQ 후보 추출

**진행 상태: 완료 기록 있음.** 양품화 매뉴얼 사이트 본문을 FAQ 자료 기준으로 정하고 38건의 통합 원본을 준비했다. 이후 참고자료를 별도 마이그레이션으로 반영했다.

- `yangwiki`의 FAQ 근거 대상 파일 목록을 만든다.
- 대상 본문을 확인하고 질문·답변 후보를 추출해 출처를 연결한다.
- 카테고리·주제 후보를 분류하고 중복·충돌·오래된 내용·확인 불가 항목을 표시한다.
- 완료 기준: 대상 파일과 추출 결과의 대조가 끝나고, 각 후보가 승인·검토·제외·통합 중 하나의 상태를 가진다.

### Phase 2. 대표 FAQ 검토와 데이터 기준 확정

**진행 상태: 완료 기록 있음.** 제목·내용 형식, 자동 ID, 주제 분류, 키워드 및 38건 승인·1건 제외 기준을 확정했다.

- 대표 항목의 제목·내용·분류·검색 키워드를 검토한다.
- 자동 생성 ID·`created_at` 처리와 내용 형식, 검색 사례, 키워드 작성 기준을 확정한다.
- 완료 기준: 사용자 검토를 거친 대표 FAQ와 분류·ID·콘텐츠 필드 기준이 준비된다.

### Phase 3. DB 제품·스키마·초기 데이터 설계

**진행 상태: 구현됨.** MySQL·Spring Boot·Gradle Groovy를 선택했고 V1~V6로 스키마·초기 데이터·열람 이력·주제 정리를 구현했다. V7~V15는 양품화·유지보수·OS별·시스템·일반 운영 FAQ를 보완하고, V16은 FAQ 본문 가독성, V17은 양품화 수량·동의서·학교 예산 일괄 구매 및 수리 견적 정보를 보완한다. V7~V17의 각 DB 적용 여부는 확인해야 한다.

- 로컬 DB는 MySQL로 정했으며, 운영 서버 실행·호스팅 환경은 배포 단계에서 결정한다.
- FAQ, 회원·권한, FAQ 열기 집계 구조 및 키워드 저장 방식을 설계한다.
- 승인된 대표 FAQ를 초기 데이터 형식으로 변환하고 필수 값·자동 생성 ID·외래 키 연결·분류·검색어 형식을 확인한다.
- 완료 기준: 사용자 승인된 스키마와 대표 데이터, 화면별 API 계약이 준비된다.

### Phase 4. DB·서버 API·인증 구현

**진행 상태: 구현됨.** 세션 인증, FAQ 조회·검색·열람, 관리자 회원 API와 통계 API를 구현했다. 브라우저·권한별 통합 검증은 남아 있다.

- DB 스키마와 초기 데이터를 구성한다.
- 로그인·로그아웃·세션·역할 확인, FAQ 검색·목록·ID 조회, 답변 열기 집계, 관리자 회원 CRUD를 구현한다.
- 완료 기준: API에서 인증 및 권한별 동작과 데이터 저장을 확인한다.

### Phase 5. FAQ 사이트 API 연동

**진행 상태: 구현됨.** 프런트엔드 검색·FAQ·로그인·회원 관리·홈 대시보드·통계 페이지를 API에 연결했다. 기능별 브라우저 회귀 확인은 남아 있다.

- FAQ JSON 직접 요청과 브라우저 임시 인증·회원 저장을 API 기반으로 교체한다.
- 기존 검색·필터·페이징·URL 상태·직접 링크 흐름을 유지한다.
- 완료 기준: 사이트 주요 기능이 실제 API 데이터로 동작하고 권한에 따라 차단된다.

### Phase 6. 통합 검증과 배포 준비

**진행 상태: 현재 작업 단계.** 검색·최근 검색 기록, 상세 열기·조회 집계, 미인증·상담원 권한 차단, 통계 집계, 데이터 정확성, 모바일·접근성 검증이 남아 있다. 배포 환경도 정해야 한다.

- 데이터 정확성, 검색 사례, 권한, 직접 접근, 세션 만료, 오류 상태, 접근성·모바일을 확인한다.
- 운영 DB·서버·배포 구성을 정하고 환경 변수와 복구 절차를 정리한다.
- 완료 기준: 기존 기획의 인수 기준을 확인하고 배포 환경에서 주요 흐름을 검증한다.

## 7. Phase 운영과 승인

- 한 번에 현재 Phase만 수행한다.
- 각 Phase 시작 시 목표·수정 대상·완료 기준을 확인한다.
- 완료 보고에는 실제 변경 파일과 수행한 검증만 기록한다.
