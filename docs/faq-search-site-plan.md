# FAQ 검색 사이트 개발 기획안

> 역할: FAQ 사이트의 제품 목표·기능 범위·사용자 흐름·운영 요구사항 기준. 저장소 공통 작업 규칙은 루트 `AGENTS.md`, FAQ 콘텐츠와 DB 상세 기준은 각각 담당 문서를 따른다.

- 작성일: 2026-11-10
- 목적: 기존 자료를 FAQ 데이터로 정리해 별도의 검색 사이트로 배포
- 현재 단계: Spring Boot·MySQL·Flyway·세션 인증 API와 실제 FAQ 사이트 연동 구현. 대시보드·통계 화면 구현. 통합 회귀 확인과 배포 준비는 남아 있다.
- 기존 매뉴얼 프로젝트: 현재 사이트와 운영 구조 유지

## 1. 기획 평가와 보완 결과

아래 점수는 요구사항의 명확성, 개발 가능성, 운영 준비도를 기준으로 한 자체 설계 평가다. 실제 구현·사용성·성능 테스트 결과가 아니다. 기준은 요구사항의 명시 여부와 완료 조건의 구체성이며, 각 항목은 배점 범위에서 평가했다.

| 평가 요소 | 배점 | 기존안 | 보완안 | 문제와 보완 내용 |
|---|---:|---:|---:|---|
| 목적·범위 | 15 | 13 | 14 | 독립 사이트 목표는 명확하지만 작업 경계가 부족함. 기존 매뉴얼 사이트와 구분되는 프런트엔드·백엔드·배포 경로를 명시 |
| 데이터 구조·ID | 15 | 11 | 14 | FAQ 6개 필드 기준을 유지하고 DB 자동 증가 ID와 등록 시각을 사용하며, 사용 빈도 집계는 별도 테이블로 분리 |
| 콘텐츠 이관 | 10 | 7 | 9 | 질문 분리 기준만 있고 전체 추출의 누락 방지 절차가 없음. 목록화·중복 정리·보류 항목 대조 절차 추가 |

보완의 핵심은 FAQ 콘텐츠 필드를 늘리지 않고, 사용 빈도와 열람 이력은 별도 테이블로 관리하는 것이다. 현재 선택은 MySQL, Java·Spring Boot, Gradle Groovy, Docker Compose 로컬 DB, 서버 세션 인증이다. 이 문서는 구현 기준과 현재 적용 상태를 함께 기록한다.

## 2. 목표와 사용자

콜센터 상담원이 검색어를 입력하거나 대분류를 직접 탐색해 질문 답변을 바로 확인하는 사이트를 만든다. 로그인한 상담원은 FAQ를 조회하고, 관리자는 회원 계정을 조회·개설·수정·삭제한다. 인증되지 않은 사용자는 FAQ 내용과 검색 기능에 접근할 수 없다.

일반 사용자의 검색 흐름은 다음과 같다.

> 로그인 → 좌측 `검색` 선택 → 검색어 입력 → 질문 제목 목록 → 답변 펼치기 → 필요 시 답변 복사

FAQ 목록 조회 흐름은 다음과 같다.

> 로그인 → 좌측 `FAQ` 선택 → 상단 카테고리 선택(선택 사항) → 질문 목록 → 답변 펼치기 → 필요 시 답변 복사

관리자 흐름은 다음과 같다.

> 관리자 로그인 → 회원 목록 조회 → 계정 개설·수정 또는 계정 삭제

권한은 상담원과 관리자 두 종류로 구분한다. 상담원 계정 권한은 고정하며 일반 사용자는 FAQ 조회 기능만 사용할 수 있다. 관리자는 FAQ 조회와 회원 계정 조회·개설·수정·삭제를 할 수 있다. 인증·권한 검사는 서버에서 수행하며, 미인증 요청에 FAQ 데이터나 검색 결과를 반환하지 않는다.

홈 대시보드는 최근 7일 조회수 순 FAQ, 로그인 사용자별 최근 열람 FAQ, 당일 조회 주제를 표시한다. 통계 화면은 양품화 사업과 유지보수의 대분류·기간별 열람 현황을 제공한다. 개인별 추천은 범위에 포함하지 않는다.

## 3. 범위와 기존 자료의 관계

새 사이트는 기존 매뉴얼 사이트와 별도의 서비스로 개발한다. 현재 저장소에서는 `frontend/`와 `backend/`를 분리 관리하고, 배포 시 별도 서비스 주소를 사용한다. 기존 HTML 파일을 새 사이트 화면으로 그대로 옮기지 않고, 본문을 FAQ 데이터로 추출한다.

| 기존 자료 | 처리 방향 |
|---|---|
| 양품화 사업 안내 | 상담 질문 단위로 분리하고 해당 답변에 필요한 조건·절차를 함께 유지 |
| 학교 측 업무 프로세스 | 작업별 질문으로 전환하고 순서가 필요한 답변은 번호 목록으로 유지 |
| 유지보수 FAQ | 원문 질문·답변을 우선 사용. 임의의 정책·확인 문구를 추가하지 않음 |
| 유지보수 상세·재배치·문의 안내 | 독립된 질문에 답할 수 있는 항목을 추출 |
| 추가 운영 메모·별도 첨부 파일 | FAQ 원문 범위에서 제외. FAQ는 양품화 매뉴얼 사이트 본문 기준 |
| FAQ 자료 범위 | 양품화 매뉴얼 사이트 본문. 사이트가 언급한 별도 파일은 확인 범위에서 제외 |
| 공통 JS의 검색 색인 | 이미 본문에서 추출한 내용을 중복 등록하지 않음 |
| 메뉴·목차·패치내역·개발 검토 문서 | 콘텐츠 추출 대상 목록에는 기록하되 FAQ 답변으로 등록하지 않음 |

전체 자료를 목록화한 뒤 FAQ 전환 여부를 결정한다. 작업용 대조 목록은 이관 검토 문서로 두며, FAQ 데이터의 필드를 늘리지 않는다.

## 4. DB 구조와 저장 방식

FAQ 한 건을 하나의 `faqs` 레코드로 저장한다. 프런트엔드는 인증된 API를 통해 MySQL 데이터를 조회한다. 운영 FAQ/API의 콘텐츠 기준은 `id`, `category`, `topic`, `title`, `content`, `keywords` 여섯 항목이다. 컬럼 자료형과 관계를 포함한 확정 논리 스키마는 [DB 스키마 설계안](DB-스키마-설계-초안.md)을 따른다.

| 표시명 | JSON 필드 | 형식 | 필수 | 작성 규칙 |
|---|---|---|---|---|
| ID | id | 정수 | 필수 | MySQL이 자동 생성. 새 FAQ 등록 시 직접 입력하지 않음 |
| 구분 | category | 문자열 | 필수 | 합의한 대분류 중 하나 |
| 주제 | topic | 문자열 | 필수 | 구분 안의 소분류 중 하나 |
| 제목 | title | 문자열 | 필수 | 한 가지 업무 주제를 나타내며 질문형으로 제한하지 않음 |
| 내용 | content | 문자열 | 필수 | 근거가 확인된 안내·조건·예외·절차를 포함 |
| 검색어 | keywords | 문자열 배열 | 선택 | 별칭·약어·기기명·자주 사용하는 다른 표현. 없으면 빈 배열 |

출처·검토 상태·검토 메모는 운영 FAQ 및 공개 API 필드에 포함하지 않는다. 연도·기기·OS·학교 유형에 따른 적용 차이는 FAQ 내용에 구분해 보존한다.

대분류는 `2027년 양품화 사업`, `유지보수`, `2027년 디벗 재배치·여분기기 수거 사업` 세 가지로 구성한다. 주제는 실제 콘텐츠를 추출한 뒤 각 대분류 안에서 이름을 통일한다. 카테고리별 FAQ 테이블은 나누지 않는다. `faqs.category_id`가 `faq_categories.id`를 참조하고, API에서는 조인한 카테고리 표시명을 `category`로 제공한다. `faq_categories`는 `id`, `name`만 두며 이름 중복을 금지한다. `code`와 `sort_order`는 두지 않는다.

핵심 테이블은 `faq_categories`, `faqs`, `faq_keywords`, `faq_usage_stats`, `users`이며, V5에서 사용자별·기간별 열람 통계를 제공하기 위한 `faq_view_history`를 추가했다. FAQ는 `id`, `category_id`, `topic`, `title`, `content`, `created_at`을 저장한다. 키워드는 `(faq_id, keyword)` 복합 기본키로 FAQ 내부 중복을 막고, 동일 키워드는 서로 다른 FAQ에서 사용할 수 있다. FAQ 삭제 시 키워드·집계·열람 이력을 함께 삭제하며, 연결 FAQ가 남은 카테고리는 삭제를 제한한다. 계정은 `users`에 로그인 ID, 해시값을 저장하는 `password`, 역할을 저장한다. 별도 표시 이름 없이 화면에는 `username`을 표시한다.

확정 자료형은 ID `BIGINT UNSIGNED AUTO_INCREMENT`, 카테고리명·주제·키워드 `VARCHAR(100)`, 제목 `VARCHAR(255)`, 내용 `TEXT`, 등록 시각 `DATETIME DEFAULT CURRENT_TIMESTAMP`, 조회 수 `BIGINT UNSIGNED NOT NULL DEFAULT 0`, 사용자 비밀번호 해시 `VARCHAR(255)`, 역할 `VARCHAR(20)`이다. 문자열 컬럼은 `utf8mb4`를 사용한다. ID·등록 시각·조회 수는 DB 관리 항목이며 사람이 입력하지 않는다.

자주 조회되는 FAQ 정렬에 사용할 빈도는 FAQ 본문 필드에 넣지 않고 별도 집계 테이블로 관리한다. FAQ 콘텐츠와 조회 행동 데이터를 분리한다.

| 테이블 | 필드 | 형식 | 규칙 |
|---|---|---|---|
| faq_usage_stats | faq_id | FAQ `id`와 동일한 정수 형식, 기본 키·외래 키 | FAQ 한 건당 집계 행 하나. FAQ 삭제 시 함께 삭제 |
| faq_usage_stats | open_count | 정수, 기본값 0 | 답변이 실제로 열릴 때마다 1 증가 |

집계는 로그인한 사용자가 질문을 펼쳐 답변을 연 시점에만 기록한다. 목록 노출, 검색 결과 표시, 답변 닫기는 집계하지 않는다. 사용자 ID·IP·개별 클릭 이력은 저장하지 않고 FAQ별 총 열기 횟수만 저장한다. 같은 세션에서 닫았다 다시 열면 새로운 열기 1회로 집계한다.

FAQ 행이 없는 동안에도 전체 목록을 정렬할 수 있도록 조회 시 집계 테이블을 FAQ와 외부 조인하고, 없는 횟수는 0으로 처리한다. 랭킹 조회를 위한 `open_count` 인덱스는 실제 데이터 규모와 실행 계획을 확인한 뒤 적용한다.

MySQL 구현 시 FAQ ID를 외래 키로 연결하고, 동시 요청에서도 증가가 유실되지 않도록 원자적 증가 쿼리를 사용한다. 개념 예시는 `INSERT ... ON DUPLICATE KEY UPDATE open_count = open_count + 1`이다. 집계 API는 서버에서 로그인 상태와 FAQ ID를 확인한 뒤 처리한다.

다음은 구조 설명용 예시이며 실제 운영 FAQ가 아니다.

```json
[
  {
    "id": 1,
    "category": "유지보수",
    "topic": "수리 접수",
    "title": "수리 접수 방법은 무엇인가요?",
    "content": "검토를 마친 원문 근거 기반 안내 내용이 들어갑니다.",
    "keywords": ["AS", "A/S", "고장 접수"]
  }
]
```

내용은 제한된 Markdown 형식으로 저장한다. 문단, 줄바꿈, 목록, 굵은 글씨, 표를 지원해 기존 표·체크리스트의 의미를 유지한다. 원시 HTML과 스크립트는 허용하지 않는다.

## 5. 자동 ID와 등록 시각 규칙

FAQ `id`는 MySQL 자동 증가 정수로 생성한다. 항목을 등록할 때 사람이 ID를 정하지 않으며, 등록 시각은 별도 `created_at` 컬럼에 DB가 자동 기록한다. ID는 항목을 참조하는 식별자이고 등록 시각은 등록 날짜·시간을 나타내므로 두 값을 구분해 사용한다.

- 새 FAQ 등록 요청과 초기 데이터 입력에서는 `id`를 생략하고 DB가 만든 값을 사용한다.
- 한 번 발급된 ID는 수정·분류 변경 후에도 유지한다. 새 FAQ를 분리해 만들면 DB가 새 ID를 발급한다.
- 삭제한 ID를 다시 직접 지정하거나 자동 증가 값을 초기화하지 않는다. 자동 증가 번호에 빈 번호가 생길 수 있으며, 연속 번호 자체를 보장하지 않는다.
- 최근 등록순은 `created_at` 내림차순, 같은 시각이면 `id` 내림차순으로 정렬한다.
- 기존 `data/faq.json`의 문자열 ID는 화면 시연용으로 유지한다. API 연동 때에는 DB가 발급한 숫자 ID와 URL을 사용하도록 변환한다.

## 6. 콘텐츠 추출·정리 규칙

1. 양품화 매뉴얼 사이트 HTML 페이지를 대상으로 본문을 추출한다.
2. 이미 완성된 FAQ는 질문과 답변을 그대로 가져온다. 문단·목록·표의 표시 형식만 정돈한다.
3. 일반 설명문은 실제 내용에 답이 있는 질문으로 나눈다. 답변에 없는 절차·정책·가격을 만들지 않는다.
4. 같은 질문과 같은 답변은 하나로 합친다. 기기·연도·조건이 달라 답변이 달라지는 경우는 해당 조건이 드러나는 제목으로 분리한다.
5. 한 답변 안의 연속된 작업 순서나 예외 조건을 지나치게 쪼개지 않는다. 검색 결과 하나만 열어도 답변을 이해할 수 있어야 한다.
6. 내부 검토 문구와 반복되는 일반 확인 지침은 답변에 덧붙이지 않는다. 원문에 있는 실제 접수·문의 절차는 보존한다.
7. 자료 간 충돌은 작업용 검토 목록에 기록하고 내용이 정리된 후 등록한다. 사이트에 임의의 결론을 만들지 않는다.
8. 구체적인 학교·학생·계정·비밀번호 등 사례 정보는 공개 데이터에 포함하지 않는다. 신청서에 필요한 항목명과 실제 개인정보 값은 구분한다.
9. 추출한 각 항목이 등록·중복 통합·제외·검토 중 어느 상태인지 작업용 목록과 대조해 누락을 확인한다.

등록할 FAQ 수는 추출 후 확정한다. 기존 페이지 개수나 원문 화면의 전체 FAQ 수를 이관 완료 수량으로 대신하지 않는다.

## 7. 검색과 정렬

검색 대상은 ID, 제목, 내용, 키워드다. 구분과 주제는 필터로 제공한다. 내용을 새로 생성하는 AI 기능 없이 저장된 FAQ를 검색한다.

| 항목 | 동작 |
|---|---|
| 입력 방식 | 입력이 끝난 뒤 약 200ms 후 검색. 한글 조합 중에는 실행하지 않고 조합 완료 후 반영 |
| 기본 정규화 | 앞뒤 공백 제거, 연속 공백 정리, 영문 대소문자 구분 없음 |
| 띄어쓰기 | 띄어쓰기를 제거한 검색도 보조적으로 사용. 애플펜슬/애플 펜슬 등을 함께 찾음 |
| 별칭 | AS, A/S, 에이에스 등은 검색어 필드로 연결. 자동 오타 교정은 초기 범위에서 제외 |
| 복수 단어 | 입력 단어가 모두 제목·답변·검색어 중 어딘가에 포함된 FAQ를 검색 |
| 결과 우선순위 | ID 정확 일치 → 제목 정확 일치 → 제목 구절 일치 → 제목·검색어의 단어 일치 → 내용 일치 |
| 같은 순위 | 제목 일치 수가 많은 항목 우선, 이후 `created_at`·ID 기준으로 일관된 순서 유지 |
| 검색 결과 없음 | 검색어 변경과 필터 초기화 버튼 제공. 무관한 FAQ를 일치 결과로 표시하지 않음 |
| 빈 검색어 | 현재 필터에 해당하는 전체 목록 표시 |
| 검색 홈 기본 정렬 | 검색어가 비어 있으면 `open_count` 내림차순으로 자주 열린 질문을 먼저 표시. 같은 횟수는 등록 시각 최신순 |
| 검색어가 있는 결과 | 검색 정확도 우선순위를 유지하고 사용 빈도로 검색 관련도를 덮어쓰지 않음 |
| FAQ 목록 화면 | 상단 카테고리 필터로 조회하며 최근 등록순으로 표시 |
| 집계 전·0회 데이터 | 집계 행이 없거나 모두 0이면 `created_at` 최신순으로 대체 |

현재 검색은 프런트엔드가 입력 중 250ms 디바운스로 API를 호출하며, 서버가 ID·제목·내용·키워드 검색과 필터·페이징을 처리한다. FAQ 열기는 누적 `faq_usage_stats`와 개별 `faq_view_history`에 기록한다. 입력 중 결과 갱신은 유지하고 최근 검색어 기록은 Enter 확정 시에만 저장한다. IME 한글 조합 중 Enter와 최근 검색 칩 선택은 검색 기록을 새로 만들지 않는다.

## 8. 화면과 사용자 동작

로그인하지 않은 사용자는 로그인 화면으로 안내한다. 인증되지 않은 사용자가 FAQ 페이지 경로를 직접 열거나 FAQ 데이터 주소를 요청해도 내용을 받을 수 없어야 한다. 로그인 성공 후 권한에 맞는 화면으로 이동한다.

일반 사용자 화면에는 좌측 공통 탐색 메뉴를 둔다. `검색`은 검색 중심 홈으로 이동하고, `FAQ` 아래에는 대분류별 메뉴를 둔다. FAQ 화면은 목록을 기본으로 표시하며 상단 카테고리 선택으로 전체 또는 특정 대분류를 조회한다. 좌측 대분류 메뉴도 같은 FAQ 목록의 선택 필터로 연결한다. 검색 홈과 FAQ 목록 화면은 별도로 유지한다.

좌측 메뉴 전체와 FAQ 대분류 하위 메뉴는 각각 접고 펼칠 수 있다. 메뉴 상태는 현재 탭에서 페이지 이동 후에도 유지한다. 모바일에서는 좌측 메뉴가 가로 탐색 메뉴로 바뀌며 FAQ 하위 메뉴를 별도로 접고 펼친다.

검색 홈은 검색창, 검색 결과 수, 질문 목록, 페이지 이동을 중심으로 구성한다. 검색 결과 목록에서는 질문 제목을 중심으로 보여주고 선택한 제목 아래에 답변을 펼친다. FAQ 탐색 화면에서는 선택한 대분류 안의 질문을 등록일 기준으로 표시하고 검색 없이 목록을 둘러볼 수 있게 한다.

- 검색 전에는 제목 목록을 표시한다. 검색 중에는 일치한 답변의 짧은 일부를 함께 표시할 수 있다.
- 한 페이지에 20건을 표시한다. 이전·다음 버튼, 현재 페이지, 전체 페이지 수를 표시한다.
- 검색어 또는 필터를 바꾸면 첫 페이지로 이동한다.
- 구분을 변경하면 이전 주제 선택을 초기화하고 해당 구분의 주제만 제공한다.
- 여러 답변을 동시에 펼쳐 비교할 수 있다.
- 검색어가 없는 검색 홈은 FAQ 열기 횟수순으로 표시하고, 검색어가 있으면 검색 관련도순을 유지한다. FAQ 목록 화면은 최근 등록순을 유지한다.
- 답변을 열 때만 서버에 FAQ 열기 이벤트를 보내 누적 집계와 사용자별 열람 이력을 기록한다. 닫기·목록 노출은 기록하지 않는다. 개별 이력은 최근 열람 목록과 기간별 통계 집계에 사용한다.
- 최근 검색어는 현재 브라우저의 사용자별 `sessionStorage`에 저장한다. 입력 중 디바운스 결과는 기록하지 않고 Enter로 확정한 검색어만 기록한다. 최근 검색 칩 선택은 결과만 실행한다.
- 답변 복사 버튼은 제목과 답변을 복사한다. 복사 실패 시 직접 선택해 복사할 수 있는 안내를 제공한다.
- 자동 생성된 FAQ ID로 해당 내용을 여는 주소를 만든다. 예: `?faq=1`. DB에 주소 필드를 저장하지 않는다.
- 검색어·필터·페이지 상태는 URL에 반영한다. 연속 타이핑마다 브라우저 방문 기록을 쌓지 않는다.
- 삭제되었거나 없는 ID로 접근하면 항목을 찾을 수 없다는 안내와 전체 목록 이동 버튼을 제공한다.
- 키보드로 검색·필터 선택·답변 열기·페이지 이동이 가능하게 하고, 펼침 상태와 결과 수를 보조기기에 전달한다.
- 모바일 표는 답변 영역 안에서 가로로 스크롤하게 하고, 페이지 전체가 옆으로 밀리지 않게 한다.

관리자 화면에서는 회원 목록 검색·조회, 상담원 계정 개설·수정·삭제를 제공한다. 일반 사용자 화면에는 회원 관리 진입점과 기능을 제공하지 않는다.

## 9. 개발 구조와 데이터 표시

현재 프런트엔드는 HTML·CSS·JavaScript 모듈로 구성되며 Spring Boot API와 MySQL에 연결된다. 서버 세션 인증, FAQ 조회·검색·열람 이력, 관리자 회원 API와 통계 API가 구현돼 있다. 로컬 브라우저에서 로그인 및 FAQ 목록 표시를 확인했으며 세부 기능의 통합 검증과 배포는 남아 있다.

```text
frontend/
  index.html
  faq.html
  login.html
  admin.html
  stats.html
  components/
    header.html               # 공통 브랜드·계정 메뉴
    footer.html               # 공통 개발자 정보
    faq-sidebar.html          # 검색·FAQ 대분류 공통 탐색 메뉴
  assets/
    img/k-one-mark.svg
    img/chevron-down.svg       # 공통 선형 화살표 아이콘
    img/copy.svg               # FAQ 답변 복사 아이콘
    css/common.css            # 공통 기본값·헤더·푸터·도움말
    css/style.css             # FAQ 페이지 전용
    css/browse.css            # 대분류 탐색 화면 전용
    css/auth.css              # 로그인·관리자 페이지 전용
    js/app.js
    js/api.js                 # 백엔드 API·세션 쿠키·CSRF 요청
    js/browse.js              # FAQ 대분류 탐색 화면
    js/search.js
    js/render.js
    js/auth.js
    js/stats.js               # 통계 화면 및 차트 렌더링
    js/components.js          # 공통 HTML 조각 로드·헤더 상태 처리
  data/faq.json              # 이전 정적 시연 자료; 현재 API 화면의 데이터 원본은 아님
```

| 구성 | 책임 |
|---|---|
| app.js | 데이터 로드, 검색·필터·페이징 상태, URL 상태 복원 |
| browse.js | FAQ 목록, 대분류 필터, 페이지 상태 표시 |
| search.js | 문자열 정규화, 필터링, 검색 순위 계산 |
| render.js | 결과 목록·답변 표시, 강조 표시, 복사·접근성 처리 |
| auth.js | 서버 세션 로그인·로그아웃과 관리자 회원 API 화면 처리 |
| components.js | 공통 헤더·푸터·FAQ 메뉴 삽입과 계정·선택 메뉴 상태 관리 |
| api.js | FAQ·인증·회원·통계 API 요청, 세션 쿠키 및 CSRF 처리 |
| stats.js | 통계 필터와 일별·주제별·FAQ별 차트 표시 |
| common.css | 공통 기본 스타일, 헤더·푸터, 툴팁 스타일 |
| 페이지별 CSS | 각 화면 고유의 레이아웃과 요소 스타일 |
| faq.json | 이전 화면 시연 자료. 현재 FAQ 조회는 백엔드 API 사용 |

`app.js`와 `browse.js`는 API를 이용해 검색·필터·서버 페이징·URL 상태를 관리한다. `render.js`는 FAQ 내용과 목록을 표시하고, `api.js`는 API 요청과 인증 관련 처리를 담당한다. 로컬 개발은 정적 HTTP 서버와 Spring Boot를 각각 실행한다. 데이터 로딩·실패·빈 결과 상태는 화면에서 구분한다.

로그인과 권한 판정은 Spring Security 서버 세션에서 처리한다. 비밀번호는 서버에서 BCrypt로 검증·저장하고 회원 변경은 DB API에 반영한다. `frontend/data/faq.json`은 레거시 시연 파일로 남아 있으나 현재 화면에서 사용하지 않는다. 검색은 Spring 백엔드의 MySQL 조회 로직으로 수행하며 검색 품질·한국어 별칭 사례는 추가 검증 대상이다.

FAQ 조회·로그인·회원 관리 화면은 API 응답을 사용한다. FAQ 콘텐츠는 여섯 항목을 유지하고, 검색 키워드·누적 열기 횟수·사용자별 열람 이력·사용자 계정은 각각 책임에 맞는 테이블에서 관리한다. 검색은 MySQL `LIKE` 방식으로 구현돼 있으며, 데이터 규모나 검색 품질이 부족할 때 전문 검색 도입을 다시 검토한다.

## 10. 관리 원본과 배포 절차

SQL 초기 데이터의 검토 원본은 `docs/FAQ-DB-통합-원본.md`다. 승인된 항목만 DB 초기 데이터로 변환한다. 이 문서는 현재 후보 검토와 초기 적재 준비용이며, 장기 운영 시 FAQ를 편집·검토할 관리 원본의 형식(문서·시트·관리 화면)은 아직 확정하지 않는다. 어떤 형식을 선택해도 새 FAQ ID는 DB가 생성하며 등록 시각은 `created_at`으로 기록한다.

FAQ 열기 횟수는 서버가 관리하는 `faq_usage_stats`에 누적하고, 기간·사용자별 열람 이력은 `faq_view_history`에 저장한다. 이를 통해 대시보드와 통계 화면의 집계를 제공한다. FAQ 본문을 다시 반영해도 집계가 덮어쓰이지 않도록 콘텐츠 마이그레이션과 이용 기록을 분리한다.

> 통합 원본 작성 → 내용 검토·승인 → DB 초기 데이터 변환·검증 → 미리보기 → 배포 → 배포 주소에서 확인

콘텐츠 수정은 추후 확정할 관리 원본에서 진행한다. 변환 결과에 필수 값 누락·분류 오류·미승인 내용이 있으면 배포를 중단한다. 이전 배포 데이터와 파일을 버전 관리해 문제 발생 시 함께 되돌린다. 코드와 데이터 버전이 섞이지 않도록 한 배포 단위로 반영한다.

운영 DB·백엔드 호스팅·프런트엔드 배포 주소와 도메인은 미결정이다. 서버 세션 인증과 API 권한 검사는 구현돼 있다. 배포 전 CORS 허용 도메인, HTTPS 쿠키 속성, 비밀값 주입, 로그아웃·세션 만료 시 보호 동작을 운영 환경에서 확인한다.

## 11. 개발 단계와 산출물

| 단계 | 작업 | 산출물·완료 조건 |
|---|---|---|
| 1. 프런트엔드 시연 | 검색·FAQ 목록·필터·페이징·답변 펼침·임시 로그인 화면 | 완료. 일부 화면 구조는 API 연동 후에도 활용 |
| 2. FAQ·DB·API | FAQ 정리, MySQL 스키마·V1~V8 마이그레이션, 세션 인증·FAQ·회원·통계 API | 구현 파일 존재. 각 로컬 DB의 최신 마이그레이션 적용 상태 확인 필요 |
| 3. 화면 연동 | 검색·FAQ·로그인·회원 관리·대시보드·통계 화면을 API에 연결 | 구현 완료. 검색·조회 이력·권한·통계 등 브라우저 회귀 확인 필요 |
| 4. 통합 검증 | 데이터 정확성, 검색 사례, 권한, 직접 접근, 세션 만료, 접근성·모바일 확인 | 진행 필요 |
| 5. 배포·운영 준비 | 운영 환경·비밀값·백업·복구·계정 발급 및 배포 | 미착수 |

추출할 분량과 검토 보류 수량을 확인하기 전에는 전체 개발 일정을 확정하지 않는다. 대표 FAQ로 데이터와 검색 구조를 먼저 확인한 후 전체 이관 규모를 산정한다.

## 12. 완료·검증 기준

아래는 개발 시 수행할 검증 계획이며, 이 기획서 작성 단계에서 실행한 결과가 아니다.

| 영역 | 인수 기준 |
|---|---|
| 데이터 | DB 자동 생성 ID의 중복 0건, 필수 값 누락 0건, 등록 시각 생성 확인 |
| 내용 | 등록 FAQ가 검토 원문과 일치하고 금액·기한·조건·예외 누락 0건. 충돌 미해결 항목은 등록 완료 수량에서 제외 |
| 이관 | 모든 후보 항목의 등록·통합·제외·검토 중 처리 결과가 대조 목록에 기록됨 |
| 검색 | 대표 검색 30개 중 27개 이상에서 의도한 FAQ가 첫 5개 결과 안에 표시됨. 숫자 ID 정확 검색은 전부 해당 항목을 첫 번째로 표시 |
| 한국어 입력 | 한글 조합 중 잘못된 검색 실행 없이 입력 완료 후 결과 반영. 띄어쓰기·별칭 사례 확인 |
| 화면 | 20건 페이징, 필터 변경 시 첫 페이지 이동, 결과 수와 실제 목록 일치 |
| 이용 빈도 | 답변이 열릴 때 집계 1회 증가, 목록 노출·답변 닫기는 미집계. 빈 검색 홈은 집계 내림차순, 동률·0회는 `created_at` 최신순. 검색어 결과는 관련도순 유지 |
| 직접 접근 | FAQ ID 주소와 브라우저 뒤로 가기에서 답변·검색 상태가 의도대로 복원됨 |
| 접근성·모바일 | 키보드만으로 주요 작업 가능. 360px 폭에서 페이지 전체 가로 넘침 없음 |
| 인증·권한 | 로그인하지 않은 상태에서 FAQ 화면·데이터/API 직접 접근이 모두 차단됨. 상담원은 FAQ 조회만 가능하고 회원 관리 불가. 관리자는 회원 조회·개설·수정·삭제 가능 |
| 오류 | JSON 로드 실패·빈 데이터·없는 ID·검색 결과 없음에 각각 적절한 화면 제공 |
| 성능 | 초기 기준 데이터 1,000건에서 입력 대기시간 제외 검색·목록 갱신 200ms 이내 목표. 측정 기기·브라우저를 기록하고 실제 데이터로 재평가 |
| 운영 | 관리 원본 수정 → 변환 → 미리보기 → 배포 및 이전 버전 복구 절차를 실제로 수행 가능 |

검색 사례에는 `애플펜슬`, `애플 펜슬`, `AS`, `A/S`, `펜슬 분실`, `환불`, `무인보관함`, 정확한 FAQ ID, 결과가 없는 검색어를 포함한다. 주요 업무 구분별로 사례를 분산한다.

## 13. 후속 검토 항목

대시보드와 통계 화면은 구현됐다. 검색 품질과 실제 사용 패턴을 확인한 뒤 자동 오타 교정이나 검색 인덱스 도입을 검토한다. 데이터가 커져 검색 목표를 충족하지 못하면 먼저 응답 시간과 쿼리 실행 계획을 측정한 후 확장한다.

현재 설계 평점 92점에서 남은 과제는 실제 데이터 규모, 대표 검색 결과, 운영 담당자의 편집·배포 경험을 확인하는 것이다. 이 항목들은 문서상의 점수만으로 검증된 것으로 보지 않는다.
